# Agentic AI Loan Approval Demo
## Data-Layer Documentation

### 1. Project Overview
The demo uses fictional loan applicant data to demonstrate how a bank loan assessment workflow can organise applicant information, review documents, assess affordability, identify risk indicators and support a human credit officer's decision.

### 2. Current Data Sources

**MySQL database**
- Database: `loan_approval_demo`
- Main applicant table: `applicants`
- Additional tables: `document_verifications` and `officer_decisions`
- Applicant records stored: 100

**CSV data layer**
- File: `lakehouse_applicants.csv`
- Records: 100
- Columns: 15
- Purpose: Provides a structured, portable dataset for data inspection, analysis and potential future cloud ingestion.

### 3. Data Fields
The CSV includes:
- Applicant name and application ID
- Monthly income and existing EMI
- Requested loan amount and tenure
- Credit score and risk level
- Estimated EMI and EMI ratio
- Application status
- KYC, salary slip, bank statement and bureau statuses

### 4. Current Data Flow
1. Fictional applicant records are generated by the Python application.
2. Applicant records are stored in MySQL.
3. Python retrieves applicant data from the database.
4. The data preparation script produces `lakehouse_applicants.csv`.
5. The Streamlit application uses applicant information in its assessment workflow.
6. Rule-based checks generate findings and a preliminary recommendation.
7. A human credit officer reviews the result and records a decision.

### 5. Validation Status
- CSV contains 100 applicant records.
- CSV contains 15 columns.
- No missing cells were detected in the exported CSV.
- No duplicate rows were detected.
- Financial calculations and assessment rules require separate validation.

### 6. Current Limitations
- Applicant data is fictional and intended for demonstration.
- Google BigQuery is not connected.
- The CSV is an exported data file, not a live-synchronised lakehouse.
- The current assessment uses Python rules and simulated checks; it is not a live AI-agent or banking integration.
- Document statuses and officer decisions are stored using the application's current database implementation.
- The demo does not make real lending decisions or disburse funds.

### 7. Proposed Future Architecture
Subject to available access and cost considerations, Google BigQuery may be introduced as a cloud analytical data layer. A future implementation could ingest structured applicant data and additional approved document metadata, apply data-quality checks, and provide curated datasets to the application.

Any future cloud connection, automated document extraction, live credit bureau integration or LLM-powered agent must be implemented and tested before being described as operational.

### 8. Security and Governance
- Use fictional data for demonstrations.
- Never commit database credentials or API keys to source control.
- Restrict access to applicant information.
- Record human decisions and assessment rationale.
- Clearly distinguish automated recommendations from authorised lending decisions.

### 9. Current Implementation Summary
**Implemented:** MySQL storage, CSV export, Python-based assessment rules, simulated document checks and human decision recording.

**Not implemented:** BigQuery connection, live external data integrations and LLM-powered agents.
